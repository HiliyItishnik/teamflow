# Ежедневная работа команды

Третий этап добавляет браузерный интерфейс, поиск, личные фильтры и устойчивую очередь
уведомлений. Миграция `V6` сохраняет существующие данные; `V1`–`V5` не изменены.

## Интерфейс

После `scripts/start.ps1` открой [TeamFlow](http://localhost:8080/).
HTML, CSS и JavaScript поставляются в том же Spring Boot JAR; Node/npm и отдельный
frontend-сервер для запуска не нужны. Swagger остаётся на `/swagger-ui/index.html`.

Доступны вход, регистрация, запрос и применение кода восстановления пароля,
создание рабочих пространств и проектов, переключение проектов, архивирование,
доска с тремя статусами, создание/редактирование задач, выбор исполнителя,
комментарии и история, участники проекта, приглашения и принятие кода.
Автор комментария и его текст отображаются как обычный текст, без интерпретации HTML.
Редактирование и удаление отдельных комментариев доступны через REST API; в карточке
интерфейса сейчас есть чтение и добавление комментариев.

Статус меняется в карточке задачи. Перетаскивание карточек пока не добавлено.
Доска показывает **30 задач текущей страницы**, распределённых по колонкам;
счётчики колонок относятся к этой странице. Общее количество найденных задач и
переключение страниц показаны отдельно. Это сохраняет серверную фильтрацию и пагинацию.
Для узкого экрана колонки прокручиваются горизонтально, карточка открывается на всю ширину.

Access/refresh token находятся только в памяти вкладки. После перезагрузки страницы
нужен вход; localStorage, sessionStorage и cookies для токенов не используются.
Refresh выполняется одним запросом на вкладку, даже если несколько API-запросов
одновременно нуждаются в обновлении. При недоступности сети запись не повторяется автоматически.
Для задач и комментариев повтор неизменённой формы использует прежний Idempotency-Key.
Редактирование отправляет версию из открытой карточки. При `412` форма остаётся на экране;
кнопка «Перечитать карточку» явно предупреждает о замене несохранённых полей.

Статические страницы имеют CSP без inline-скриптов и внешних CDN. Публичен только
интерфейс входа и его ресурсы; данные API по-прежнему защищает Spring Security.
Уведомления проверяются раз в 15 секунд, пока вкладка видима. Доска обновляется
после действий пользователя и применения фильтра; WebSocket и фоновая синхронизация доски не добавлены.

## Поиск и просроченные задачи

`GET /api/v1/workspaces/{workspaceId}/projects/{projectId}/tasks`

| Параметр | Поведение |
| --- | --- |
| `q` | До 200 символов; подстрока в названии или описании, без учёта регистра; пробелы по краям удаляются |
| `overdue=true` | Срок меньше сегодняшней даты UTC, статус не DONE; задачи без срока исключены |
| `status`, `priority`, `assigneeId` | Прежние фильтры, применяются вместе с новыми через AND |
| `page`, `size` | Пагинация после всех условий, размер 1–100 |

`%`, `_` и `\` в поиске — обычные символы, не шаблоны SQL. Пустой `q` и `overdue=false`
не добавляют ограничение. Поиск выполняется внутри доступного проекта, включая архивный.
Отдельный полнотекстовый индекс и ранжирование не добавлены; замеры на больших данных — этап 4.

## Сохранённые фильтры

Путь: `/api/v1/workspaces/{workspaceId}/projects/{projectId}/filters`.

- `GET` — массив собственных фильтров пользователя, максимум 50 на проект.
- `POST` — создать; `201` и ETag. Тело: `name`, `q`, `status`, `priority`, `assigneeId`, `overdue`.
- `PUT /{id}` — заменить настройки, нужен `If-Match`; версия увеличивается.
- `DELETE /{id}` — удалить с `If-Match`, `204`.

Название — 1–80 символов, уникально для владельца внутри проекта. Другой участник,
включая ADMIN, не видит и не меняет личный фильтр. Перед действием снова проверяется
доступ к проекту. Фильтры разрешены и в архиве, поскольку не меняют содержимое проекта.
Если исполнитель ушёл из проекта, UUID в фильтре сохраняется: такой запрос может дать пустой результат.
При удалении проекта или пользователя фильтры удаляются каскадно.

## Уведомления внутри приложения

- `ASSIGNED`: задача назначена другому пользователю; повтор того же назначения не создаёт событие.
- `COMMENTED`: новый комментарий получают остальные участники проекта, кроме автора.
- Самоназначение, снятие исполнителя, редактирование комментария и повтор POST с тем же
  Idempotency-Key не создают дополнительные уведомления.

Получатели фиксируются при действии. На доставке и при каждом чтении заново проверяется
доступ к проекту; потеря доступа скрывает и список, и счётчик. Отсутствие доступа на момент
доставки означает пропуск события без повторов. Архивирование сохраняет доступ для чтения.
В уведомлении показывается актуальное название задачи; тела комментариев в очереди нет.

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/v1/notifications?unread=true&page=0&size=20` | Собственные доступные уведомления, пагинация 1–100 |
| `GET /api/v1/notifications/unread-count` | `{count: …}` |
| `PUT /api/v1/notifications/{id}/read` | Пометить прочитанным, повтор безопасен; чужое/недоступное — `404` |
| `PUT /api/v1/notifications/read-all` | Прочитать все собственные доступные уведомления |

## Очередь и повторная обработка

`background_jobs` записывается **в той же транзакции**, что назначение или комментарий.
Если очередь не записалась, бизнес-изменение тоже откатывается. Планировщик каждые 2 секунды
обрабатывает до 20 заданий. Несколько экземпляров делят работу через `FOR UPDATE SKIP LOCKED`
([документация PostgreSQL](https://www.postgresql.org/docs/17/sql-select.html#SQL-FOR-UPDATE-SHARE)).

Получение задания коммитит lease на 60 секунд и уникальный `claim_id`. После остановки
процесса просроченный lease может забрать другой обработчик. Старый обработчик не может
завершить задание с чужим claim. Создание уведомления и завершение задания атомарны;
уникальный `notifications.event_id` предотвращает дубликат.

При ошибке доставка откатывается, а отдельная транзакция записывает номер попытки,
название класса ошибки и следующее время запуска. До 5 попыток; задержки 2, 4, 8, 16 секунд.
После пятой ошибки или истечения последнего lease выставляется `failed_at`.
Ошибка не выводит payload, email или токен в логи. Завершённые/ошибочные задания и связанные
уведомления удаляются через 30 дней; очистка ежечасная. Удаление задачи сразу удаляет её события.

### Восстановление пароля

Запрос `forgot` теперь сначала коммитит задание, затем возвращает `202`. Очередь переживает
перезапуск. В задании находится нормализованный email, **не код и не пароль**. Проверка аккаунта,
генерация кода и SMTP выполняются обработчиком; новые запросы замещают устаревшие ещё не отправленные.
Без настроенной почты endpoint по-прежнему возвращает `503`.

SMTP не участвует в транзакции PostgreSQL: при сбое после принятия письма сервером письмо
может прийти повторно, а код из незакоммиченной попытки не сработает. При успешном повторе
действует последний код. Гарантия отсутствия дублей относится к уведомлениям в БД, **не к email**.
После 5 ошибок запроси новое письмо после устранения причины. Неизвестные аккаунты дают
тот же `202`, затем задание завершается без отправки. Email удаляется с записью задания по retention.

### Диагностика оператором

В изолированной административной сессии БД можно проверить ошибки без чтения адресов:

```sql
SELECT id, kind, attempts, last_error, available_at, failed_at
FROM background_jobs WHERE failed_at IS NOT NULL ORDER BY failed_at DESC;
```

После исправления причины повторить конкретное ошибочное задание:

```sql
UPDATE background_jobs
SET attempts = 0, failed_at = NULL, last_error = NULL,
    claim_id = NULL, leased_until = NULL, available_at = now()
WHERE id = '<проверенный UUID задания>'::uuid AND failed_at IS NOT NULL;
```

Публичного API управления очередью нет. Для тестов планировщик отключается свойством
`teamflow.jobs.enabled=false`; сами сервисы обработки остаются доступны тестам.
Метрики очереди, распределённые ограничения нагрузки и production-настройки вынесены в этап 4.

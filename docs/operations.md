# Эксплуатация TeamFlow

## Поиск запроса в логах

Каждый запрос получает новый UUID в `X-Request-ID`; переданный клиентом заголовок игнорируется.
Для ошибок API тот же UUID находится в `ProblemDetail.requestId`, включая ошибки валидации,
неправильный JSON и отказ Spring Security. По нему можно найти строку в `docker compose logs app`.

Лог доступа содержит HTTP-метод, шаблон маршрута, код ответа и длительность в миллисекундах.
Вместо `/tasks/<UUID>` записывается `/tasks/{taskId}`. До выбора маршрута записывается `unmatched`.
Параметры поиска, тела, заголовки, пароли и токены в лог доступа не попадают.
MDC очищается в `finally`, чтобы идентификатор не переходил следующему запросу в том же потоке.

## Метрики

Обычный запуск сохраняет публичный `/actuator/health` без деталей. Профиль `operations`
переносит management-endpoints, включая health, на отдельный порт, по умолчанию `127.0.0.1:9090`.
В конфигурации HTTPS Caddy направляет публичный health именно на этот порт.
Нужен отдельный случайный `OPERATIONS_KEY` длиной минимум 32 байта. Пустой или короткий ключ
закрывает доступ; JWT обычного пользователя и роль workspace ADMIN не дают права читать метрики.
`/actuator/info` также требует ключ оператора. `/actuator/env`, heapdump и прочие endpoints не открываются.

```powershell
$env:SPRING_PROFILES_ACTIVE = 'operations'
# OPERATIONS_KEY хранится в окружении оператора/секретах, не в исходниках.
Invoke-RestMethod http://127.0.0.1:9090/actuator/metrics -Headers @{
    'X-Operations-Key' = $env:OPERATIONS_KEY
}
```

`/actuator/prometheus` принимает тот же заголовок. Prometheus можно запускать на этом же сервере;
для удалённого доступа используй SSH-туннель. В конфигурации VPS Caddy не пропускает `/actuator/*`,
кроме публичного health; management-порт публикуется только на loopback хоста.
В обычном локальном Compose профиль не включён; см. [конфигурацию VPS](deployment.md).

| Метрика Micrometer | Назначение |
| --- | --- |
| `http.server.requests` | Число и время HTTP-запросов с тегами шаблона маршрута, метода и статуса |
| `hikaricp.connections.*` | Соединения PostgreSQL, занятые/ожидающие, время получения соединения |
| `jvm.*`, `process.*` | Память, GC, потоки и процесс JVM |
| `teamflow.workspace.lock` | Время вызова `SELECT … FOR UPDATE` рабочего пространства: SQL + ожидание блокировки |
| `teamflow.jobs{state=pending/leased/failed}` | Снимок числа ожидающих, обрабатываемых и окончательно неуспешных заданий |
| `teamflow.jobs.oldest.pending.seconds` | Возраст самого старого ожидающего задания, включая отложенный повтор |
| `teamflow.jobs.snapshot.errors` | Неудачные обновления снимка очереди |

Снимок очереди обновляется одним агрегирующим SQL раз в 30 секунд, первый раз через 5 секунд.
При ошибке остаются прежние значения и увеличивается счётчик ошибок. Статистика не содержит email,
UUID пользователя/задачи и текста уведомлений. В histogram HTTP нет тегов с идентификаторами запросов.
Профиль включает histogram HTTP и блокировки; исходные значения Prometheus используют секунды.
Таймер блокировки — время каждого обращения к блокирующему SELECT, а не чистое ожидание PostgreSQL.
`pg_stat_activity.wait_event_type='Lock'` помогает отдельно подтвердить ожидание.

## Резервная копия и пробное восстановление

Работает с PostgreSQL текущего локального Compose либо с явно переданным `-Container`.
Нужны Docker и PowerShell 5.1+; Java на хосте не нужна.

```powershell
.\scripts\backup.ps1
.\scripts\verify-backup.ps1 -Backup .\backups\teamflow-<дата>-<id>.dump

# Для отдельного развёртывания:
$db = docker compose --env-file deploy/.env -f deploy/compose.yml -p teamflow-prod ps -q postgres
.\scripts\backup.ps1 -Container $db
.\scripts\verify-backup.ps1 -Container $db -Backup <путь-к-копии>
```

`pg_dump --format=custom` создаёт согласованный снимок БД без остановки приложения.
Файл переносится через `docker cp`, без двоичного перенаправления PowerShell 5.1.
Рядом создаётся JSON-манифест с SHA-256, временем и версией pg_dump; существующие файлы не перезаписываются.
SHA-256 обнаруживает повреждение файла, но не удостоверяет его происхождение.

Проверка создаёт новую БД `teamflow_restore_<случайный UUID>`, восстанавливает одной транзакцией
с `--exit-on-error --no-owner --no-acl`, проверяет текущую версию Flyway, валидность ограничений
и связи задач/проектов/пространств/участников/исполнителей. Выводятся только числа записей.
После проверки удаляется только созданная ею временная БД и временный файл контейнера.
Отдельно проверь возможность входа и прикладные сценарии перед переключением настоящего приложения.

Восстанавливай только доверенные копии: архив содержит SQL и функции. Нужна версия PostgreSQL,
совместимая с форматом архива; здесь pg_dump/pg_restore идут из того же контейнера PostgreSQL 17.
Проверка ожидает схему текущего checkout; старую копию сначала восстанавливают в изолированное
окружение соответствующей версии, затем применяют более новые миграции.

Копия содержит персональные данные, хеши паролей, сессии и email очереди. Каталог `/backups/`
исключён из Git и Docker build, но само резервирование не шифрует файл. Ограничь права каталога,
шифруй внешнее хранилище и храни хотя бы одну копию вне сервера. JWT_SECRET и SMTP-настройки
в pg_dump не входят: их нужно резервировать отдельно в хранилище секретов.

Начальная политика: ежедневная копия, 7 ежедневных и 4 еженедельных; проверка восстановления
после изменения схемы и хотя бы раз в месяц. Это инструкция: расписание и внешнее хранилище
ещё не настроены. RPO зависит от фактического расписания; RTO нужно измерить на выбранном сервере.

## Восстановление после сбоя

1. Остановить запись (`docker compose … stop app`), сохранить текущие логи и повреждённый том.
2. Создать отдельную пустую БД/контейнер PostgreSQL 17. Проверить копию скриптом выше.
3. Восстановить доверенный архив в новую БД через pg_restore; восстановить секреты приложения.
4. Запустить тот же либо более новый JAR, дождаться Flyway и health. Проверить вход, чтение задач,
   права, запись комментария и очередь. Вернуть трафик только после этих проверок.
5. Старый том сохранить до завершения расследования. Проверить время копии и возможную потерю изменений.

Скрипт проверки специально не умеет перезаписывать рабочую БД. Команда `down --volumes`
применяется только автоматической проверкой к своему случайному Compose-проекту.

[Micrometer-метрики Spring Boot](https://docs.spring.io/spring-boot/3.5/reference/actuator/metrics.html),
[pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html),
[pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html).

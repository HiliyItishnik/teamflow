# Надёжность API: этап 1 развития TeamFlow

Этап добавляет проверку версии при изменении карточек, защиту создания от повторных запросов,
архивирование проектов и диагностику запуска. Миграция `V4` сохраняет существующие данные;
все прежние проекты остаются активными.

## Изменение контракта: ETag и If-Match

Ответы с одной карточкой workspace, проекта, задачи или комментария содержат поле `version`
и заголовок `ETag`. Его значение нужно сохранить **вместе с данными, которые редактирует пользователь**.
Пример: `"52e07b8d-d2ad-42ea-a99c-ed4d369df799:3"`.
Списки содержат `id` и `version` карточек; перед открытием формы можно прочитать отдельную карточку.
Добавлен `GET .../tasks/{taskId}/comments/{commentId}`.

Следующие операции требуют `If-Match` с ETag соответствующей карточки:

| Ресурс | Операции |
| --- | --- |
| Workspace | `PUT`, `DELETE` |
| Проект | `PUT`, `DELETE`, `PUT .../archive` |
| Задача | `PUT`, `DELETE`, `PUT .../assignee` |
| Комментарий | `PUT`, `DELETE` |

Добавление/удаление участников и смена роли продолжают использовать прежние URL и транзакционные
проверки; они не требуют ETag карточки workspace или проекта.

```http
GET /api/v1/workspaces/{workspaceId}/projects/{projectId}/tasks/{taskId}
Authorization: Bearer <token>

### В следующем запросе передай ETag из ответа GET, включая кавычки
PUT /api/v1/workspaces/{workspaceId}/projects/{projectId}/tasks/{taskId}
Authorization: Bearer <token>
If-Match: "52e07b8d-d2ad-42ea-a99c-ed4d369df799:3"
Content-Type: application/json

{"title":"Обновлённая задача","status":"DONE","priority":"HIGH"}
```

- Нет заголовка — `428 Precondition Required`.
- Версия изменилась или ETag принадлежит другой карточке — `412 Precondition Failed`.
- Поддерживается один точный ETag; `*`, слабые теги `W/` и списки тегов отклоняются с `400`.
- После успешного изменения ответ содержит актуальные `version` и `ETag`.
- Сохранение тех же значений может оставить прежнюю версию: фактического изменения нет.
- Авторизация выполняется до проверки версии, чтобы не раскрывать чужие ресурсы.

При `412` прочитай свежие данные и предложи пользователю сравнить изменения. Автоматическое
получение новой версии перед отправкой старой формы уничтожает смысл защиты.
В [демо](demo.md) ETag хранится с последним полученным ответом, а устаревший запрос проверяется отдельно.

**Совместимость:** прежние клиенты, которые изменяли карточки без `If-Match`, получат `428`.
Примеры `requests/teamflow.http` и `scripts/demo.ps1` обновлены. В Swagger возьми ETag из ответа
GET/POST и передай его в параметре `If-Match` следующей операции.

## Создание без дубликатов

`POST .../projects/{projectId}/tasks` и `POST .../tasks/{taskId}/comments` принимают
необязательный заголовок `Idempotency-Key` в формате UUID.

```http
Idempotency-Key: d4c207dc-6974-4e61-93df-4173a1ad849b
```

Клиент генерирует ключ один раз на действие пользователя. Если ответ потерялся или произошёл
таймаут, повторяет тот же запрос с тем же ключом. Для нового действия нужен новый UUID.

| Ситуация | Результат |
| --- | --- |
| Первый запрос с ключом | Создание и `201` |
| Повтор с тем же телом и ключом | Тот же `201`, исходное тело и ETag, без нового ресурса |
| Тот же ключ, другое тело | `409` |
| Ключ не является UUID | `400` |
| Заголовок отсутствует | Обычное создание; защиты от дубликатов нет |

Ключ изолирован по пользователю и адресу коллекции. Одинаковый UUID можно использовать
для другой коллекции или другого пользователя без получения чужого ответа.
Хеш вычисляется из DTO после разбора JSON: порядок полей в JSON не влияет на повтор.
Пробелы внутри значений строк являются частью запроса.

Ответ сохраняется в `creation_requests` в одной транзакции с задачей/комментарием и историей.
Сбой откатывает и ресурс, и запись о ключе. Перед повтором заново проверяются доступ и архивное состояние.
Два одновременных повтора сериализуются блокировкой workspace.

Сохраняется **исходный ответ**: после изменения или удаления ресурса повтор не создаёт его заново.
У такого ответа ETag может быть устаревшим; для дальнейшей работы выполни GET по ID.
Записи о ключах хранятся до удаления проекта или автора. Автоматического срока очистки пока нет:
это сохраняет защиту от поздних повторов, но требует учёта роста таблицы при эксплуатации.

## Архив проектов

ADMIN может выполнить `PUT .../projects/{projectId}/archive` с телом `{"archived":true}`
и актуальным ETag проекта. Для восстановления используется тот же URL и `{"archived":false}`.
Ответ содержит `archived`, `version` и ETag.

Список проектов по умолчанию возвращает активные. `?archived=true` возвращает только архивные;
фильтрация по доступу и состоянию происходит до пагинации.

Архив сохраняет задачи, назначения, комментарии, историю и участников. Чтение разрешено
тем же пользователям. Изменение проекта, его задач, комментариев и состава проекта возвращает `409`.
Восстановление возвращает возможность редактирования.

Управление доступом на уровне workspace продолжает работать: удаление участника команды
отзывает доступ и может снять назначения также в архивных проектах.
ADMIN по-прежнему может явно удалить проект с актуальным ETag. Это необратимое каскадное удаление;
архивирование — отдельная операция, DELETE не превращён в скрытое архивирование.

## Порядок блокировок

Изменения содержимого проекта и его архивного состояния берут `PESSIMISTIC_WRITE` на workspace
до чтения ресурса и проверки версии. Это упорядочивает архивирование, изменение членства и запись данных.
`@Version` и ограничение уникальности записи истории продолжают действовать.
Условные изменения при конфликте версии возвращают `412`; обычные конфликты целостности — `409`.

Такой порядок прост, но сериализует изменения внутри команды, включая разные задачи.
Это осознанное ограничение текущего монолита; перед уменьшением области блокировки нужны
замеры ожидания блокировок и сохранение тестов конкурентных сценариев.

## Запуск с диагностикой

```powershell
# Подготовка ключа, проверка окружения, затем запуск Compose
.\scripts\start.ps1

# Только диагностика: ничего не устанавливает и не меняет
.\scripts\check-env.ps1

# PostgreSQL уже запущен отдельно, DB_* заданы в текущем терминале
.\scripts\start.ps1 -Mode Local
```

`start.ps1` останавливается, если обязательная проверка не пройдена.
`check-env.ps1 -Mode Docker` проверяет ключ, Docker CLI, Linux-движок, Compose и локальные порты;
Java на компьютере не требуется. На Windows при недоступном движке проверяется состояние виртуализации.

`-Mode Local` проверяет Java 21, наличие компилятора, JWT из окружения, формат JDBC URL
и доступность TCP-порта PostgreSQL. Проверку логина, пароля, существования БД и схемы выполняет
приложение при старте. Скрипт не выводит значения секретов.

Занятый порт — `WARN`: это может быть уже запущенный TeamFlow. Скрипт не останавливает чужие процессы.
Команды Docker ограничены ожиданием 15 секунд. Никакие настройки BIOS, WSL и политики PowerShell
скрипты не меняют. Для запрета запуска `.ps1` см. [диагностику Windows](testing.md#если-запуск-не-удался).

## Проверки

`ReliabilityApiIT` проверяет устаревшие формы всех четырёх типов карточек, назначение исполнителя,
одновременные изменения с одним ETag, повторы создания, границы ключей, сохранение ответа после удаления,
отзыв доступа, откат транзакции, архивирование и восстановление.
Тест миграции проходит цепочку `V2 → V3 → V4 → V5` с существующими данными.
CI запускает этот набор вместе с прежними тестами, диагностикой и HTTP-демо в Docker Compose.

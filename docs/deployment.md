# Подготовка HTTPS-демо

Публичный сервер и домен пока не выбраны. Конфигурация ниже готовит отдельное развёртывание
Java-монолита с PostgreSQL и Caddy; локальная TLS-проверка не является публикацией в интернете.

## Локальная проверка

```powershell
# PowerShell 7.2+, Docker; использует случайные свободные порты и временные данные
pwsh -File .\scripts\check-deployment.ps1
```

Скрипт собирает JAR в Docker, запускает отдельный Compose-проект, проверяет TLS на `localhost`,
интерфейс, health, перенаправление HTTP → HTTPS и защиту API/метрик. Проверяет адрес OpenAPI
и невозможность обхода IP-лимита поддельными заголовками. Создаёт двух пользователей,
пространство, проект, задачу, назначение, комментарий и два задания очереди; проверяет их число
и связи после backup/restore. Доверяет только созданному Caddy корню внутри одного HTTP-клиента;
системное хранилище сертификатов не меняется, проверка имени и цепочки TLS не отключается.
В конце удаляет только свои контейнеры и тома. Артефакты и копия остаются в игнорируемом `target/`.
Это проверка конфигурации и локального сертификата, а не проверки DNS/ACME публичного домена.

## Запуск на VPS

Нужны Linux-сервер с Docker Compose, DNS A/AAAA на этот сервер и доступные снаружи TCP 80/443.
Приложение и PostgreSQL не публикуют свои рабочие порты. Caddy автоматически получает и обновляет
сертификат публичного домена; его данные хранятся в отдельном томе.

1. Склонировать репозиторий на сервер. Доступ к приватному репозиторию настроить отдельно.
2. Создать `deploy/.env` из `deploy/.env.example`, ограничить доступ к файлу (`chmod 600 deploy/.env`).
3. Задать домен без `https://`, email сертификата, отдельный случайный пароль PostgreSQL,
   Base64 `JWT_SECRET` и отдельный `OPERATIONS_KEY` (каждый секрет минимум 32 случайных байта).
4. Выполнить из корня репозитория:

```bash
docker compose --env-file deploy/.env -f deploy/compose.yml -p teamflow-prod up --build -d
docker compose --env-file deploy/.env -f deploy/compose.yml -p teamflow-prod logs --tail=100 app caddy
```

Переменные окружения текущего терминала имеют приоритет над `.env`: не используй случайно
переменные локальной TLS-проверки. Публичное имя должно слушать стандартный HTTPS-порт 443.
Параметры `HTTP_BIND`, `HTTP_PORT`, `HTTPS_PORT`, `HTTPS_CONTAINER_PORT` предназначены для локальной проверки;
на VPS оставь значения по умолчанию. Не открывай management-порт наружу.
Секреты передаются через окружение контейнеров и доступны администратору Docker; не публикуй
вывод `docker compose config`/inspect и не выдавай пользователям доступ к Docker socket.

База и секреты здесь относятся к новому развёртыванию. Изменение `POSTGRES_PASSWORD` в `.env`
не меняет пароль роли в уже созданном PostgreSQL. Для переносимых секретов можно позднее
перейти на Compose secrets и Spring configtree, согласовав имена свойств.

## Доверенный прокси

В VPS-конфигурации включены профили `operations,proxy`. Второй использует стандартный
Tomcat RemoteIpValve: `TRUSTED_PROXY_ADDRESS` превращается в точное совпадение адреса
через регулярное выражение `\Q<адрес>\E`. Доверия ко всем private/loopback-сетям нет.
Для обычного запуска профиль не активен, `forward-headers-strategy=none` сохраняется.

Caddy имеет постоянный IPv4 в выделенной сети: по умолчанию `PROXY_ADDRESS=172.30.240.10`
в `PROXY_SUBNET=172.30.240.0/24`. Backend подключён к этой сети и отдельной внутренней сети БД;
PostgreSQL подключён только к внутренней сети, Caddy не имеет прямого доступа к БД.
При конфликте подсетей с Docker/VPN выбери свободную /24 и соответствующий адрес Caddy
в `deploy/.env` перед запуском. Они должны принадлежать одной подсети; gateway обычно `.1`,
адрес прокси не должен совпадать с gateway/другим контейнером. Проверка использует отдельную случайную /24.

Caddy перезаписывает `X-Forwarded-For` адресом TCP-клиента и `X-Forwarded-Proto` фактической
схемой, `X-Forwarded-Host` — hostname запроса, принятого маршрутизатором Caddy,
`X-Forwarded-Port` — настроенным внешним `HTTPS_PORT`. Клиентский `Forwarded` удаляется.
Tomcat принимает эти значения только от настроенного адреса прокси. Это сохраняет HTTPS
и внешний порт в OpenAPI/Swagger и разделяет IP-лимиты пользователей.

Эта схема рассчитана на один Caddy непосредственно перед приложением. Не подключай CDN,
балансировщик или ещё один прокси без отдельной настройки доверия: Caddy пока считает клиентом
свой непосредственный TCP-peer. Несколько пользователей за общим NAT по-прежнему делят IP-лимит;
лимиты по email независимы. Не публикуй backend 8080 и не добавляй посторонние контейнеры
в сеть proxy. Менять адрес Caddy и список доверия нужно согласованно.

Проверки `ProxyClientIpIT` работают с реальным Tomcat и двумя исходными loopback-адресами,
а не с MockMvc: посторонний peer не может подменить IP/схему/hostname; доверенный разделяет
лимиты и передаёт HTTPS/порт. `DirectClientIpIT` проверяет выключенное доверие по умолчанию.
TLS-сценарий также вращает поддельные IP через настоящий Caddy и получает `429` с `Retry-After`.

## Проверка после запуска

Проверь `https://<домен>/`, `/actuator/health`, Swagger и сценарии с отдельными аккаунтами.
Метрики читай по loopback 9090 с ключом оператора (см. [operations.md](operations.md)).
Swagger открыт для демонстрации контракта API; сами бизнес-маршруты требуют JWT.
Регистрация публичная, автоматической очистки демо-аккаунтов нет. Не используй реальные командные
данные в публичном учебном демо; заранее настрой ограничения диска, резервирование и мониторинг.

## Обновление и откат

Перед обновлением записать commit SHA, создать и проверить копию БД. После `git pull --ff-only`
выполнить `docker compose … up --build -d app`. При изменениях Caddy выполнить тот же запуск
для caddy и проверить логи. Один экземпляр приложения может быть временно недоступен во время перезапуска.

Откат JAR допустим только при совместимой схеме. Flyway не выполняет обратные миграции:
при несовместимой схеме восстанавливай копию в отдельную БД и переключай приложение после проверки.
Нельзя откатывать схему удалением строк Flyway или правкой опубликованной миграции.

Набор контейнеров останавливается через `docker compose … down` без `--volumes`.
Потеря тома caddy_data потребует повторного получения сертификатов; потеря postgres_data — восстановления БД.

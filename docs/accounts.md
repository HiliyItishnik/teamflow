# Вход, сессии и присоединение к команде

Второй этап развития добавляет миграцию `V5`. Пользователи, пароли и команды сохраняются.
**После обновления нужно войти заново:** старые JWT без `sid` больше не принимаются.
Запуск новой версии: `scripts/start.ps1`. Миграции `V1`–`V4` не изменены.

## Сессии

Регистрация и вход возвращают `accessToken`, `tokenType`, `expiresIn`, `user`,
`refreshToken`, `sessionId`, `refreshExpiresAt`. Access token живёт 15 минут;
сессия и refresh token — до 30 дней с момента входа, без продления абсолютного срока.
В БД хранятся только SHA-256-хеши случайных 256-битных refresh-токенов.

| Метод и путь после `/api/v1/auth` | Контракт |
| --- | --- |
| `POST /refresh` | Без Bearer, JSON `{"token":"<refresh token>"}`; новая пара токенов, `200` |
| `GET /sessions` | С Bearer; до 20 активных сессий, `current` отмечает текущую |
| `DELETE /sessions/{id}` | Отозвать свою сессию, `204`; чужая или неизвестная — `404` |
| `DELETE /sessions` | Отозвать все свои сессии, включая текущую, `204` |
| `POST /logout` | Отозвать текущую сессию по Bearer, `204` |

Каждый JWT содержит `sid`; Resource Server проверяет активность этой сессии в PostgreSQL
на каждом запросе. Выход, отзыв и сброс пароля блокируют уже выданные access token.
Запрос, прошедший аутентификацию до отзыва, может завершиться; отзыв не отменяет выполняющиеся транзакции.
HTTP-сессии и cookies не используются. Auth-ответы имеют `Cache-Control: no-store`.
`lastUsedAt` обновляется при refresh, а не при каждом API-запросе.

Refresh token одноразовый. Повтор использованного токена отзывает **всю его сессию**, включая
новый refresh token, и возвращает `401`. Другие устройства продолжают работать.
Клиент должен выполнять refresh последовательно и сохранять новую пару атомарно.
При потере ответа нельзя слепо повторять refresh: потребуется новый вход.
Два одновременных refresh дают `200` и `401`, после чего сессия отозвана.
Подход соответствует [ротации refresh-токенов в RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14).

Максимум 20 активных сессий на аккаунт; новый вход отзывает самые старые сверх лимита.
После окончания абсолютного срока записи сессий и история refresh удаляются с запасом в один день;
очистка выполняется ежечасно. До истечения срока история нужна для обнаружения повторов.

## Приглашения

| Метод и путь | Контракт |
| --- | --- |
| `POST /api/v1/workspaces/{id}/invitations` | ADMIN; `{"email":"member@example.test","role":"MEMBER"}`; `201` |
| `GET /api/v1/workspaces/{id}/invitations?page=0&size=20` | ADMIN; история приглашений, до 100 на страницу |
| `DELETE /api/v1/workspaces/{id}/invitations/{invitationId}` | ADMIN; отзыв, `204` |
| `POST /api/v1/invitations/accept` | Получатель с Bearer; `{"token":"<код>"}`; членство, `200` |

Создание возвращает `{invitation, token}`. **Код доступен только в этом ответе:** администратор
передаёт его получателю по доверенному каналу. Автоматическая email-рассылка приглашений пока отсутствует.
В списке и БД исходного кода нет. Приглашать можно до регистрации; получатель регистрируется
с указанным email, входит и подтверждает код. Срок — 7 дней; роль задаёт ADMIN.
Членство не создаётся до подтверждения. Вступление в workspace не добавляет пользователя во все проекты.

Повторное приглашение того же email отзывает прежнее незавершённое приглашение.
Просроченный, отозванный, принятый код и несовпадение email дают одинаковый `404`.
Отзыв уже принятого приглашения — `409`: удаляй членство обычным API участников.
Уже существующее членство не повышает роль через приглашение и даёт `409`.
Старые приглашения удаляются через 30 дней после истечения срока. API прямого добавления
зарегистрированных участников сохранён для совместимости; приглашение — отдельный путь с согласием получателя.

## Восстановление пароля

Настрой SMTP через `.env` для Compose или переменные окружения для Maven/IDE:

```dotenv
SMTP_HOST=smtp.example.org
SMTP_PORT=587
SMTP_USERNAME=teamflow@example.org
SMTP_PASSWORD=<пароль приложения SMTP>
SMTP_AUTH=true
SMTP_STARTTLS=true
MAIL_FROM=teamflow@example.org
```

STARTTLS по умолчанию обязателен, таймаут соединения, чтения и записи — по 5 секунд.
Порт 587 предназначен для STARTTLS; не подставляй порт 465 с implicit TLS без отдельной настройки.
Для изолированного локального SMTP-приёмника допустимы `SMTP_AUTH=false`, `SMTP_STARTTLS=false`.
Секреты не коммитить. Скрипт `init-env.ps1` не экспортирует SMTP-параметры для Maven/IDE: задай их явно.

1. `POST /api/v1/auth/password/forgot`, JSON `{"email":"user@example.org"}` → `202` с одинаковым сообщением
   для существующего и неизвестного аккаунта. Ответ не содержит кода.
2. В письмо приходит случайный одноразовый код со сроком 15 минут.
3. `POST /api/v1/auth/password/reset`, JSON `{"token":"<код из письма>","password":"<новый пароль>"}` → `204`.
4. Все сессии пользователя отзываются. Нужно выполнить обычный login с новым паролем.

Новый запрос кода заменяет прежний. Неизвестный, использованный или просроченный код — `401`;
невалидный пароль — `400`, код при этом не расходуется. Пароль по-прежнему имеет минимум
10 символов и максимум 72 UTF-8 байта. Сброс пароля, расходование кода и отзыв сессий атомарны.
Рекомендации по одноразовым кодам и одинаковому ответу: [OWASP Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

Проверка аккаунта и отправка выполняются после HTTP-ответа в ограниченном пуле (2 потока, очередь 100).
Без SMTP или при заполненной очереди — `503` независимо от наличия аккаунта.
`202` означает принятие запроса, а не подтверждение доставки. При ошибке SMTP код не сохраняется;
пишется только обезличенное предупреждение. Сбой между доставкой и коммитом может привести
к недействующему коду — запроси новый. Очередь пока находится в памяти, после перезапуска
неотправленный запрос нужно повторить. Надёжная очередь с повторными попытками — следующий этап.

## Ограничение попыток

- Валидные по формату запросы register/login/refresh/forgot/reset: общий лимит **60 в минуту на IP**.
- Login: дополнительно **10 попыток за 15 минут на нормализованный email**, включая успешные.
- Forgot: не более **3 писем за 15 минут на email**; превышение даёт тот же `202`, письмо не отправляется.
- Общий лимит и login возвращают `429`, ProblemDetail и `Retry-After` в секундах.

Счётчики атомарны и сохраняются в PostgreSQL независимо от отката аутентификации;
они общие для нескольких экземпляров и переживают перезапуск. Окно начинается с первой попытки,
не продлевается заблокированными запросами. Истёкшие счётчики очищаются с запасом в сутки.
IP берётся из реального соединения; `X-Forwarded-For` не считается доверенным.
При размещении за reverse proxy все клиенты пока делят IP-лимит прокси: перед публичным запуском
нужна настройка доверенных прокси и внешнего ограничения трафика. Невалидные JSON и DTO отсекаются
до контроллера и не расходуют эти счётчики. Подтверждение email при обычной регистрации не добавлено.

## Конкурентность

Изменения сессий, login и сброс пароля берут блокировку строки пользователя до проверки актуального
состояния. Refresh перечитывает использованность токена после блокировки. Повтор refresh коммитит
отзыв сессии даже при ответе `401`. Приглашения используют существующую блокировку workspace,
общую с операциями членства. Конкурентные accept/revoke не оставляют противоречивого членства.

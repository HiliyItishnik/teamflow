# Измерения производительности

## Как повторить

Нужны Java 21 и Docker. Профиль запускает отдельный HTTP-сервер со случайным портом
и PostgreSQL 17 в Testcontainers. Не направляй `TEAMFLOW_TEST_DB_*` на рабочие данные.

```powershell
.\mvnw.cmd -B -ntp verify -Pperformance
```

Эксперимент `PerformanceProbe` запускается только этим профилем, отдельно от обычных `*IT`.
Он создаёт отдельную команду, 10 проектов, 101 исполнителя и 100 000 задач по 10 000 на проект.
Задачи имеют разных исполнителей, статусы, приоритеты, сроки и текст для поиска.
Наполнение идёт SQL, без 100 000 HTTP-вызовов; это не измерение скорости создания задач.

Для каждого сценария: 5 прогревочных запросов и 100 последовательных измерений,
страница с реальными JWT, проверкой сессии/доступа, JSON и сетевым HTTP на loopback.
Измеряется время полного запроса на стороне клиента. Число Hibernate prepared statements
считается отдельно; SQL JdbcTemplate проверки сессии в этот счётчик не входит.
В каждом таком GET дополнительно выполняется один JDBC SELECT активной сессии.
Hibernate statistics включены только в эксперименте и сами добавляют накладные расходы.

Отчёт: `target/performance/report.json`, включая метаданные JVM/ОС/PostgreSQL, p50/p95/p99,
число Hibernate SQL и планы `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`.
Планы относятся к эквивалентному SELECT задач с сортировкой и LIMIT; это не планы
всех запросов авторизации, Hibernate COUNT и записи. Артефакт не содержит JWT/паролей.
В GitHub Actions есть отдельный ручной workflow **Performance probe** с JSON-артефактом на 14 дней.

## Локальный результат 3 ноября 2026

Windows 10, Java 21.0.13, PostgreSQL 17.11 в Docker, 12 доступных JVM процессоров.
Дата отчёта: `2026-11-03T13:30:00Z`. Параллелизм — 1, без TLS.
В это время также работала локальная проверка контейнерного демо; это срез на машине разработчика.

| Сценарий | p50, мс | p95, мс | p99, мс | SQL Hibernate / запрос |
| --- | ---: | ---: | ---: | ---: |
| `size=1` | 22,68 | 27,52 | 29,02 | 5 |
| `size=30` | 18,22 | 24,55 | 29,76 | 5 |
| `size=100` | 16,49 | 18,86 | 20,45 | 5 |
| `q=needle&size=30` | 24,31 | 28,91 | 30,97 | 5 |
| `overdue=true&priority=HIGH&size=30` | 15,56 | 23,52 | 25,69 | 5 |
| `page=300&size=30` | 20,25 | 24,74 | 26,90 | 5 |

SQL не увеличивается с размером страницы даже при разных исполнителях: в этом сценарии
N+1 не обнаружен. Меньшее время страницы 100 по сравнению с 1 связано с прогревом/шумом
последовательного эксперимента; это не утверждение, что большие страницы всегда быстрее.

Прямой SELECT первой страницы: обычная доска — 0,14 мс и 4 cache-hit блока,
просрочка/приоритет — 0,11 мс и 6 блоков, поиск подстроки — 7,73 мс и 186 блоков.
Поиск `lower(title/description) LIKE '%…%'` дороже, но в этом наборе укладывается в короткий ответ.
Добавлять trigram/FTS без измерений на целевом объёме пока не стали.
`COUNT` и глубокий OFFSET требуют отдельного внимания при росте числа задач внутри одного проекта.

## Проверка блокировок

Эксперимент удерживает `FOR UPDATE` строки workspace отдельным соединением, затем отправляет
HTTP-создание задачи. Ожидание подтверждается через `pg_stat_activity.wait_event_type='Lock'`.
После обнаружения ожидания блокировка удерживается ещё 400 мс и освобождается в `finally`.

Результат: HTTP-запрос 469,15 мс; максимальный таймер `teamflow.workspace.lock` — 408,32 мс.
Это подтверждает известную сериализацию записи внутри команды. Замер включает SQL, планирование
потоков и сеть, а не только чистое ожидание PostgreSQL. Разные workspace не делят одну строковую блокировку.

## Что измерить на сервере

Это не предел пропускной способности, нагрузочный тест одновременных пользователей или SLA.
100 измерений не дают устойчивой оценки хвоста p99. Порог wall-clock в CI не задан;
эксперимент проверяет успешность HTTP, ограниченное число SQL и факт ожидания блокировки.

После выбора сервера повторить с холодным/тёплым cache, несколькими размерами проекта,
параллелизмом 10/30/100 и смесью чтения/записи. Сопоставить p95/p99, ошибки, пул соединений,
CPU/GC, планы COUNT/поиска и lock waits. Менять блокировки или индексы после этих данных,
сохраняя транзакционные гарантии архивирования, прав и истории.

См. [эксплуатационные метрики](operations.md),
[PostgreSQL EXPLAIN](https://www.postgresql.org/docs/17/using-explain.html),
[pg_stat_activity](https://www.postgresql.org/docs/17/monitoring-stats.html#MONITORING-PG-STAT-ACTIVITY-VIEW).

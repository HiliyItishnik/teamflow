# TeamFlow

[![Build and test](https://github.com/HiliyItishnik/teamflow/actions/workflows/ci.yml/badge.svg)](https://github.com/HiliyItishnik/teamflow/actions/workflows/ci.yml)

Исходный код доступен в [публичном репозитории TeamFlow](https://github.com/HiliyItishnik/teamflow).

Учебная система управления командными проектами на **Java 21 + Spring Boot 3.5**.
Монолит с REST API, PostgreSQL, миграциями Flyway и разделением на controller → service → repository.

Готовая учебная версия backend: рабочие пространства, проекты, задачи, регистрация,
JWT, роли, участники проектов, исполнители, комментарии и история статусов.
Есть автоматическое демо и проверки полного сценария в CI. Локальный запуск и порты Docker Compose
по умолчанию доступны только на `127.0.0.1`. Встроенный браузерный интерфейс открывается
на главной странице; для демонстрации API также есть Swagger UI.

## Что работает

- CRUD рабочих пространств, проектов и задач.
- Браузерный интерфейс: рабочие пространства, доска, карточки, комментарии и участники.
- Поиск по названию/описанию, просроченные задачи и личные сохранённые фильтры.
- Уведомления о назначениях и комментариях; очередь PostgreSQL с повторной обработкой.
- Регистрация, вход, текущий пользователь, BCrypt и JWT Bearer.
- Refresh token с ротацией, список и отзыв сессий, выход на всех устройствах.
- Приглашения в workspace, восстановление пароля через SMTP и ограничения попыток входа.
- Роли `ADMIN` / `MEMBER` внутри рабочего пространства; управление участниками.
- Изоляция данных команд и защита последнего администратора, включая конкурентные изменения.
- Отдельные участники проектов, назначение исполнителей и фильтр задач по исполнителю.
- Комментарии с правами автора и модерацией администратора.
- История статусов с автором, временем и версией задачи; запись в одной транзакции с изменением.
- Проверка принадлежности проекта рабочему пространству и задачи проекту для чтения и изменений.
- Статусы `TODO`, `IN_PROGRESS`, `DONE`; приоритеты `LOW`, `MEDIUM`, `HIGH`; срок выполнения.
- Пагинация всех списков и фильтрация задач по статусу и приоритету.
- DTO, Bean Validation, ошибки в формате `application/problem+json`.
- UUID, время создания/обновления в UTC, транзакции и optimistic locking при конкурентных транзакциях.
- ETag/If-Match для защиты карточек от сохранения устаревших данных.
- Idempotency-Key при создании задач и комментариев; архивирование и восстановление проектов.
- PostgreSQL, Flyway, Swagger UI, Actuator health, Docker Compose и GitHub Actions.
- Идентификатор запроса в ошибках и логах, защищённые метрики HTTP/JVM/очереди/блокировок.
- Скрипты резервного копирования и восстановления в проверочную БД; конфигурация HTTPS через Caddy.
- Доверие к точному адресу Caddy и защита IP-лимитов/Swagger от поддельных Forwarded-заголовков.

## Быстрый запуск через Docker

Нужен запущенный Docker Desktop в режиме Linux containers. Java на компьютере для этого варианта не нужна.

```powershell
.\scripts\start.ps1

# Дождаться API, создать демонстрационные данные и проверить сценарии
.\scripts\demo.ps1
```

После запуска:

- TeamFlow: <http://localhost:8080/>
- Swagger UI: <http://localhost:8080/swagger-ui/index.html>
- OpenAPI JSON: <http://localhost:8080/v3/api-docs>
- Health: <http://localhost:8080/actuator/health>

Демо создаёт отдельную команду, двух её участников, два проекта и три задачи.
`start.ps1` подготавливает ключ, проверяет окружение и запускает Compose только после успешной диагностики.
Отдельная проверка: `.\scripts\check-env.ps1`. Для запуска через Maven с уже работающей БД:
`.\scripts\start.ps1 -Mode Local`.
Оно проверяет успешные запросы и ошибки доступа `401/403/404`, валидацию `400`
и защиту последнего администратора `409`. Каждый запуск использует новые учётные записи;
существующие данные не очищаются.

Скрипт выводит путь к локальному `target/demo-<id>.json` с UUID, паролями и JWT для Swagger.
Этот файл исключён из Git. Вариант без файла: `.\scripts\demo.ps1 -NoSessionFile`.
Для другого порта передай `-BaseUrl http://localhost:8081`.
На Linux/macOS демо запускается через PowerShell 7: `pwsh -File ./scripts/demo.ps1`.
Подробный сценарий показа на 5–7 минут — в [docs/demo.md](docs/demo.md).
Диагностика и backup/restore — в [docs/operations.md](docs/operations.md),
замеры на 100 000 задач — в [docs/performance.md](docs/performance.md),
подготовка HTTPS-развёртывания — в [docs/deployment.md](docs/deployment.md).
Если PowerShell запрещает выполнение `.ps1`, см. [диагностику](docs/testing.md#если-запуск-не-удался).

Логи приложения: `docker compose logs -f app`.
Остановка: `docker compose down`. Данные сохраняются в Docker volume `postgres_data`.
Значения в `.env.example` предназначены для локальной разработки. `.env` исключён из Git.

`init-env.ps1` создаёт `.env`, генерирует случайный ключ подписи JWT из 32 байтов
и загружает его в текущую PowerShell-сессию. Повторный запуск сохраняет существующий ключ.
Не копируй `.env.example` поверх настроенного `.env`.

На Linux/macOS перед первым запуском скопируй `.env.example` в `.env` и задай
`JWT_SECRET`: `export JWT_SECRET="$(openssl rand -base64 32)"`.
Сохрани ключ в локальном `.env` или хранилище секретов, чтобы он не менялся после перезапуска.

## Запуск из IDE / PowerShell

Установи JDK 21 и укажи его в `JAVA_HOME` и Project SDK в IDE.
Отдельно устанавливать Maven не нужно: в проекте есть Maven Wrapper.
Открой `pom.xml` как Maven-проект в IntelliJ IDEA.

```powershell
# Подготовить .env и JWT_SECRET в текущем терминале
.\scripts\init-env.ps1

# Запустить только базу данных
docker compose up -d postgres

# Проверить Java, затем запустить приложение
java -version
.\mvnw.cmd spring-boot:run
```

На Linux/macOS используй `./mvnw` вместо `.\mvnw.cmd`.
При необходимости: `chmod +x mvnw`.

Настройки приложения можно переопределить переменными окружения:

| Переменная | Значение по умолчанию |
| --- | --- |
| `DB_URL` | `jdbc:postgresql://localhost:5432/teamflow` |
| `DB_USERNAME` | `teamflow` |
| `DB_PASSWORD` | `teamflow_dev` |
| `SERVER_PORT` | `8080` |
| `SERVER_ADDRESS` | `127.0.0.1` |
| `JWT_SECRET` | Обязательный Base64-ключ: минимум 32 случайных байта |

Файл `.env` читает Docker Compose. Запуск через Maven или IDE не загружает его автоматически.
Скрипт `init-env.ps1` экспортирует `JWT_SECRET` в текущий терминал; в IDE укажи ключ
в переменных окружения Run Configuration (не сохраняй его в общие настройки проекта).
Если поменял параметры PostgreSQL в `.env`, передай соответствующие `DB_*` приложению:

```powershell
$env:DB_URL = 'jdbc:postgresql://localhost:5432/teamflow'
$env:DB_USERNAME = 'teamflow'
$env:DB_PASSWORD = 'teamflow_dev'
.\mvnw.cmd spring-boot:run
```

Можно использовать уже установленный PostgreSQL 17 вместо Docker: создай отдельную базу
`teamflow` и задай `DB_*`. Таблицы создаёт Flyway; Hibernate только проверяет схему
(`ddl-auto: validate`). Приложение не создаёт саму базу данных.

## Первый запрос

```powershell
$auth = Invoke-RestMethod -Method Post `
  -Uri 'http://localhost:8080/api/v1/auth/register' `
  -ContentType 'application/json; charset=utf-8' `
  -Body '{"email":"owner@example.test","displayName":"Owner","password":"Change-this-password-123"}'

$headers = @{ Authorization = "Bearer $($auth.accessToken)" }

$workspace = Invoke-RestMethod -Method Post `
  -Uri 'http://localhost:8080/api/v1/workspaces' `
  -Headers $headers `
  -ContentType 'application/json; charset=utf-8' `
  -Body '{"name":"My team","description":"Learning Java backend"}'

$project = Invoke-RestMethod -Method Post `
  -Uri "http://localhost:8080/api/v1/workspaces/$($workspace.id)/projects" `
  -Headers $headers `
  -ContentType 'application/json; charset=utf-8' `
  -Body '{"name":"TeamFlow"}'

Invoke-RestMethod -Method Post `
  -Uri "http://localhost:8080/api/v1/workspaces/$($workspace.id)/projects/$($project.id)/tasks" `
  -Headers $headers `
  -ContentType 'application/json; charset=utf-8' `
  -Body '{"title":"Build REST API","status":"TODO","priority":"HIGH"}'
```

В [requests/teamflow.http](requests/teamflow.http) есть последовательные примеры для IntelliJ HTTP Client.
Идентификаторы созданных ресурсов сохраняются автоматически в переменные следующих запросов.
Сессии, приглашения и восстановление пароля: [requests/accounts.http](requests/accounts.http).

## Авторизация и права

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/v1/auth/register` | Email, displayName, password → пользователь и access token; `201` |
| `POST /api/v1/auth/login` | Email, password → access token; `200` |
| `GET /api/v1/auth/me` | Текущий пользователь; нужен Bearer token |

Email нормализуется: пробелы по краям удаляются, регистр приводится к нижнему.
Пароль: минимум 10 символов, максимум 72 байта UTF-8 (ограничение BCrypt).
Пароли не возвращаются в API; в БД хранится только BCrypt-хеш с cost 12.

Access token живёт 15 минут. Передавай `Authorization: Bearer <accessToken>`.
В Swagger нажми **Authorize** и вставь токен. Для обновления используй `POST /api/v1/auth/refresh`
с `{"token":"<refreshToken>"}` без Bearer. Refresh одноразовый; новый сохраняй из ответа.
Сессия действует до 30 дней. Logout, отзыв сессии и сброс пароля блокируют и access token.
Сервер проверяет подпись HS256, issuer, audience, UUID subject, время действия и активность `sid` в БД.
HTTP-сессии и cookies для входа не используются. После обновления до V5 нужно войти заново.
Полный контракт сессий, приглашений, SMTP и лимитов: [вход и команда](docs/accounts.md).

| Действие | ADMIN | MEMBER |
| --- | --- | --- |
| Читать workspace и его участников | Да | Да |
| Читать проекты, задачи, комментарии и историю | Все проекты workspace | Только проекты, куда добавлен |
| Создавать, изменять, назначать и удалять задачи | Да | В своих проектах |
| Создавать, изменять и удалять проекты | Да | Нет |
| Изменять и удалять workspace | Да | Нет |
| Добавлять/удалять участников, менять роли | Да | Нет |
| Управлять составом участников проектов | Да | Нет |

Создать workspace может любой вошедший пользователь: он становится `ADMIN`.
Список workspace содержит только команды текущего пользователя.
Чужая команда и её данные возвращают `404`; недостаток прав внутри своей команды — `403`;
отсутствующий/невалидный токен или неправильный пароль — `401`.
Роли загружаются из БД при запросах, поэтому удаление/понижение участника действует
сразу для следующих запросов с уже выданным токеном. Один пользователь может иметь разные роли в разных командах.

Участники рабочего пространства:

| Метод | Путь относительно `/api/v1/workspaces/{workspaceId}` | Тело |
| --- | --- | --- |
| `GET` | `/members?page=0&size=20` | — |
| `POST` | `/members` | `{"email":"member@example.test","role":"MEMBER"}` |
| `PUT` | `/members/{userId}` | `{"role":"ADMIN"}` |
| `DELETE` | `/members/{userId}` | — |

Для прямого добавления пользователь должен уже зарегистрироваться. Альтернатива —
[приглашение по email с одноразовым кодом](docs/accounts.md#приглашения), который передаёт администратор.
Повторное добавление участника возвращает `409`. Последнего администратора нельзя удалить
или понизить: `409`. Проверка и изменение выполняются под блокировкой строки workspace.

## Командная работа в проектах

Для проекта `P = /api/v1/workspaces/{workspaceId}/projects/{projectId}` доступны:

| Метод и путь | Назначение |
| --- | --- |
| `GET P/members?page=0&size=20` | Участники проекта |
| `POST P/members` + `{"userId":"UUID"}` | ADMIN добавляет существующего участника workspace |
| `DELETE P/members/{userId}` | ADMIN удаляет участника из проекта |

Создатель проекта автоматически становится его участником. ADMIN workspace видит все его проекты
и управляет ими независимо от личного членства в проекте. Для назначения задачи пользователь,
включая администратора, должен явно состоять в проекте.
MEMBER видит только свои проекты; фильтрация выполняется до пагинации.
Скрытый проект и его задачи, комментарии, история возвращают `404`.
Добавление участника workspace само по себе больше не даёт доступ ко всем новым проектам.

Для задачи `T = P/tasks/{taskId}`:

| Метод и путь | Тело / результат |
| --- | --- |
| `PUT T/assignee` | `{"userId":"UUID"}` назначает участника проекта |
| `PUT T/assignee` | `{"userId":null}` снимает назначение |
| `GET P/tasks?assigneeId=UUID` | Фильтр по исполнителю, совместим со status/priority |
| `GET T/comments?page=0&size=20` | Комментарии от старых к новым |
| `POST T/comments` | `{"body":"Текст"}`, ответ `201` |
| `PUT T/comments/{commentId}` | `{"body":"Новый текст"}`; только автор |
| `DELETE T/comments/{commentId}` | Автор или ADMIN workspace, ответ `204` |
| `GET T/history?page=0&size=20` | История статусов в порядке версии задачи |

Задача создаётся без исполнителя. Её ответ содержит `assigneeId` (UUID или null).
Назначение — отдельная операция: обычный `PUT T` сохраняет текущего исполнителя.
Удаление из проекта автоматически снимает назначения внутри него; удаление из workspace
удаляет членство во всех его проектах и снимает соответствующие назначения.
Повторное добавление в workspace не восстанавливает прежний доступ к проектам.
Состав проекта и допустимость исполнителя защищены также внешними ключами PostgreSQL.

Комментарий содержит 1–5000 символов, автор определяется по JWT.
ADMIN может удалить чужой комментарий, но не переписать его от имени автора.
Удаление участника не стирает его комментарии и историю; доступ самого бывшего участника прекращается.
Удаление самой задачи или проекта удаляет их комментарии и историю каскадно.

История содержит `eventType`, `fromStatus`, `toStatus`, `actorId`, `actorName`, `changedAt`, `taskVersion`.
Создание задачи записывается как `CREATED`; смена статуса — `STATUS_CHANGED`.
Изменение описания, срока или исполнителя не создаёт запись о статусе.
Повторное сохранение того же статуса не создаёт дубликат. Версии могут иметь пропуски из-за других изменений задачи.
Переходы между `TODO`, `IN_PROGRESS`, `DONE` пока не ограничены отдельным workflow.
Публичных методов изменения истории нет. При конфликте версии условного изменения сервер возвращает `412`;
отклонённая транзакция не оставляет запись в истории.

## REST API

| Ресурс | Базовый путь |
| --- | --- |
| Рабочие пространства | `/api/v1/workspaces` |
| Проекты | `/api/v1/workspaces/{workspaceId}/projects` |
| Задачи | `/api/v1/workspaces/{workspaceId}/projects/{projectId}/tasks` |

Для каждого базового пути доступны:

| Метод | Путь | Результат |
| --- | --- | --- |
| `POST` | базовый путь | Создание, `201 Created` и заголовок `Location` |
| `GET` | базовый путь | Список, `200 OK` |
| `GET` | базовый путь + `/{id}` | Одна запись, `200 OK` |
| `PUT` | базовый путь + `/{id}` | Полное обновление изменяемых полей, `200 OK` |
| `DELETE` | базовый путь + `/{id}` | Удаление, `204 No Content` |

`PUT` заменяет поля соответствующего DTO: пропущенные необязательные значения очищаются.
Для задачи это title, description, status, priority и dueDate; исполнитель меняется отдельным `PUT .../assignee`.
Поля `id`, связи, `createdAt` и `updatedAt` назначает сервер. Неизвестные поля JSON отклоняются.
При создании и обновлении задачи обязательны `title`, `status` и `priority`.
`PUT` и `DELETE` карточек workspace, проекта, задачи и комментария требуют `If-Match`
с ETag из последнего ответа этой карточки. Это относится также к назначению исполнителя и архивированию.
Нет заголовка — `428`, версия устарела — `412`. Новая версия и ETag возвращаются в ответе изменения.
Методы управления участниками сохраняют прежний контракт.

Создание задачи или комментария принимает необязательный `Idempotency-Key: <UUID>`:
повтор того же запроса с тем же ключом возвращает первоначальный ответ без дубликата.
Для нового действия используй новый ключ. Архивирование: `PUT .../projects/{projectId}/archive`
с `{"archived":true}`; восстановление — `false`. В архиве содержимое доступно для чтения,
изменения запрещены. `GET .../projects?archived=true` возвращает архивные проекты, по умолчанию — активные.
Подробный контракт и ограничения: [надёжность API](docs/reliability.md).
Срок `dueDate` необязателен, формат `YYYY-MM-DD`; прошедшая дата разрешена для просроченных задач.

Параметры списков: `page` (с 0, по умолчанию 0) и `size` (1–100, по умолчанию 20).
Сортировка: `createdAt DESC, id DESC`. Задачи поддерживают `status`, `priority` и `assigneeId` одновременно:

```text
GET .../tasks?status=TODO&priority=HIGH&page=0&size=20
```

Списки возвращают `content`, `page`, `size`, `totalElements`, `totalPages`.
Несуществующий родитель или неправильная связь в URL дают `404`, некорректный запрос — `400`,
конфликт данных или запись в архивный проект — `409`, устаревший ETag — `412`, отсутствие If-Match — `428`.

**Удаление рабочего пространства удаляет все его проекты и задачи.**
Удаление проекта удаляет все его задачи. Это обеспечивают внешние ключи PostgreSQL `ON DELETE CASCADE`.

## Проверки

```powershell
# Unit-тесты и тесты HTTP-валидации, Docker не нужен
.\mvnw.cmd test

# Сборка исполняемого JAR и быстрые тесты
.\mvnw.cmd verify

# Полная проверка с PostgreSQL через Testcontainers, Docker должен работать
.\mvnw.cmd verify -Pintegration
```

Профиль `integration` запускает `*IT`: миграции, CRUD, фильтры, каскадное удаление,
регистрацию/login, проверку настоящих JWT, права ролей, изоляцию команд,
конкурентное понижение администраторов, Swagger и health. Тестовый ключ генерируется в памяти;
тестам не нужен ключ из `.env`.
Также проверяются участники проектов, назначение/удаление исполнителя, права на комментарии,
история при конкурентных изменениях, перенос данных `V2 → V3 → V4 → V5 → V6`, ETag, повторные запросы и архивирование.
Также проверяются ротация токенов, отзыв сессий, приглашения, сброс пароля и конкурентные лимиты входа.
Третий этап проверяет поиск, личные фильтры, атомарность очереди, восстановление lease и конкурентную доставку.
Эксплуатационные проверки охватывают идентификаторы запросов, доступ к метрикам и состояния очереди.
Если Docker недоступен, этот профиль завершится ошибкой, а не молча пропустит проверки.
В GitHub Actions запускается именно `verify -Pintegration`.
После него CI собирает Docker Compose и запускает тот же `scripts/demo.ps1 -NoSessionFile`,
что используется для локальной демонстрации. Тесты и демо завершаются ошибкой при нарушении ожиданий.
CI также проверяет изолированное HTTPS-демо и восстановление копии PostgreSQL.
Состав проверок и диагностика описаны в [docs/testing.md](docs/testing.md).

Для запуска тех же интеграционных тестов без Docker можно явно задать отдельную тестовую БД:

```powershell
$env:TEAMFLOW_TEST_DB_URL = 'jdbc:postgresql://localhost:55432/teamflow_test'
$env:TEAMFLOW_TEST_DB_USERNAME = 'teamflow_test'
$env:TEAMFLOW_TEST_DB_PASSWORD = 'your-test-password'
.\mvnw.cmd verify -Pintegration
```

**Указывай только одноразовую тестовую базу:** перед каждым интеграционным тестом таблицы
пользователей, рабочих пространств, участников, проектов и задач очищаются.
Обычные `DB_*` не выбирают базу для интеграционных тестов.

Результат сборки: `target/teamflow-0.1.0-SNAPSHOT.jar`.

## Границы учебной версии

Проект можно показать как Java backend с командным доступом и транзакционным аудитом.
Автоматическая рассылка приглашений и подтверждение email при обычной регистрации пока отсутствуют.
Восстановление пароля требует SMTP и использует устойчивую очередь PostgreSQL.
Интерфейс меняет статус через карточку; перетаскивание и WebSocket пока не добавлены. Публичное развёртывание потребует
HTTPS, настройки секретов и резервного копирования базы.

Четыре этапа базового roadmap завершены. Дальнейшие расширения перечислены отдельно
в [roadmap](docs/roadmap.md).

Первый этап развития после базовой версии также завершён: [надёжность API и запуска](docs/reliability.md).
Он включает изменение контракта редактирования карточек: клиентам теперь нужен `If-Match`.
Второй этап: [сессии, приглашения и восстановление пароля](docs/accounts.md).
Третий этап: [интерфейс, поиск и уведомления](docs/daily-work.md).

## Обновление базы со второго этапа

`V3` сохраняет существующие данные и добавляет текущих участников workspace в уже существующие
проекты, сохраняя их прежний доступ. Новые участники и проекты после миграции связываются явно.
Для старых задач создаётся одна запись `MIGRATED` с наблюдаемым статусом на момент обновления,
без выдуманного автора и прошлых переходов. Старые назначения отсутствуют; `assigneeId` остаётся null.

## Обновление базы с первого этапа

Flyway применит `V2` поверх `V1` без удаления прежних проектов и задач.
У старых workspace нет владельца: автоматически назначать их первому зарегистрированному
пользователю небезопасно. Они остаются скрыты, пока владелец БД явно не добавит членство.
Для новой учебной команды достаточно зарегистрироваться и создать новый workspace.
Если нужно сохранить доступ к старым данным, пример ручного назначения администратора
приведён в [архитектуре](docs/architecture.md#перенос-данных-из-этапа-1).

Версии Java/Spring Boot и Springdoc выбраны по официальным таблицам совместимости:
[Spring Boot](https://docs.spring.io/spring-boot/3.5/system-requirements.html),
[Springdoc](https://springdoc.org/v2/).
Авторизация использует стандартные компоненты [Spring Security JWT](https://docs.spring.io/spring-security/reference/6.5/servlet/oauth2/resource-server/jwt.html)
и [PasswordEncoder](https://docs.spring.io/spring-security/reference/6.5/features/authentication/password-storage.html).
